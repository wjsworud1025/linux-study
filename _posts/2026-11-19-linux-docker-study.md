## 1주차 · 파일을 만들고 백업을 자동화하기

**교재 범위** — 02-4(셸) 복습, 03장(파일 시스템과 경로), 04-2·04-4(명령 이력과 권한), 06-1·06-4(nano와 Vim), 07-1·07-3·07-5·07-6(변수·스크립트 실행·조건문·반복문)의 해당 실습.

**11/24(화) · 네 파트 시연**

1. **터미널과 이동** — 터미널과 셸의 역할을 구분합니다. Tab 자동완성, `history`, `clear`, `pwd`, `ls -l`, `ls -al`, `cd ~`, `cd -`, `cd ..`를 사용하고 같은 파일을 절대 경로와 상대 경로로 찾아갑니다.
2. **파일 조작** — `mkdir`, `touch`로 `site/index.html`을 만들고 `cat`으로 읽습니다. `cp -r`로 폴더를 복사하고 `mv`로 이름을 바꾼 뒤 `rm`으로 연습용 복사본을 지웁니다.
3. **권한** — `ls -l`의 소유자·그룹·기타 사용자 권한을 읽습니다. `chmod u+x`와 `chmod 755`를 적용해 변화를 확인하고 `sudo`가 필요한 작업을 구분합니다.
4. **편집기와 Bash** — nano로 저장한 파일을 vi/Vim으로 엽니다. `i`, `Esc`, `:wq`, `:q!`, `dd`, `yy`, `p`, `/단어`, `n`을 연습합니다. 예제 스크립트의 변수·조건문·반복문을 읽고 `./backup.sh`에서 `./`가 가리키는 경로를 설명합니다.

**11/26(목) 과제** — 소개 페이지를 작성하고 `backup.sh`를 완성합니다. 변수에 백업 경로를 담고, `if`로 폴더 존재 여부를 확인하고, `for`로 HTML 파일을 복사합니다.

**완료 기준** — 백업 폴더가 없는 상태에서 첫 실행에 성공합니다. 두 번째 HTML 파일을 추가하고 다시 실행했을 때 두 파일 모두 백업되며, 원본과 복사본의 내용이 일치합니다.

## 2주차 · 웹 서버 접속 문제 진단하기

**교재 범위** — 04-2(파일 찾기), 05-1·05-3(패키지와 프로세스), 06-2·06-3(문자 처리와 파이프라인), 07-2(환경 변수), 08-1(웹 동작 방식). 원격 접속 사례는 11-4를 참고합니다.

**12/1(화) · 네 파트 시연**

1. **로그** — `find . -name "*.log"`로 파일을 찾습니다. `head`, `tail -n`, `tail -f`, 파이프, `grep -rin`으로 특정 요청을 찾아냅니다.
2. **프로세스와 패키지** — `sudo apt update`와 `sudo apt install`의 역할을 구분합니다. `ps -ef`로 직접 실행한 서버의 PID를 찾고 `kill`로 종료합니다. `free -h`로 메모리를 확인합니다.
3. **네트워크** — `ss -tlnp`로 대기 주소와 포트를 찾고, `nc -zv 호스트 포트`로 TCP 연결을, `curl`로 HTTP 응답을 확인합니다. 루프백 주소와 모든 IPv4 인터페이스에 바인딩했을 때의 접속 범위를 비교합니다.
4. **환경변수와 SSH** — `echo "$HOME"`, `export`를 연습합니다. `ssh-keygen`으로 키 쌍을 만들고 실습 계정에 공개키를 등록한 뒤 `ssh 사용자@호스트`로 접속합니다. 개인키는 본인 기기에 보관합니다.

**12/3(목) 과제** — 팀원은 2인 1조로 준비자와 진단자를 번갈아 맡습니다. 준비자는 안내문과 다른 포트에 1주차 소개 페이지를 띄웁니다. 진단자는 서버 프로세스, 대기 포트, HTTP 응답, 접속 로그를 확인해 페이지가 열리지 않은 이유를 찾습니다.

**완료 기준** — 실제 접속 주소와 정상 페이지의 HTTP 200 응답을 제시합니다. 없는 페이지도 요청해 HTTP 404가 기록된 로그 한 줄을 찾고, 최초 접속 실패와 404의 원인을 구분해 설명합니다. 다음 주에는 같은 소개 페이지를 컨테이너에서 제공합니다.

**3주차 사전 준비 (30~45분)** — 12/8(화) 모임 전에 각자 우분투 VM에 Docker Engine과 Compose 플러그인을 설치하고 `docker run --rm hello-world`와 `docker compose version`이 성공하는지 확인합니다. VM에서 Docker를 실행할 때 관리자 권한이 필요하면 `sudo docker run --rm hello-world`로 확인합니다. [우분투용 Docker 설치 안내](https://docs.docker.com/engine/install/ubuntu/)

## 3주차 · 컨테이너로 소개 페이지 운영하기

**교재 범위** — 02-1(VM), 05-3(프로세스), 08-1(웹 요청)을 복습합니다. 이미지·컨테이너·저장소 실습은 [Docker 입문 워크숍](https://docs.docker.com/learn/paths/get-started-with-docker-containers/)을 따릅니다.

**12/8(화) · 네 파트 시연**

1. **도커 개념** — VM과 컨테이너의 구조를 비교합니다. 컨테이너가 호스트 커널을 공유하고 namespace로 실행 환경을 격리하며 cgroup으로 자원 사용을 관리하는 방식을 설명합니다.
2. **이미지** — `docker pull`, `docker images`, `docker rmi`를 익힙니다. 같은 이미지로 두 컨테이너를 띄워 이미지 레이어와 각 컨테이너의 쓰기 영역을 구분합니다.
3. **실행과 관리** — `docker run -d`와 `-p 127.0.0.1:8080:80`을 조합해 웹 서버를 실행합니다. `docker ps -a`, `docker logs`, `docker exec -it`, `docker stop`, `docker rm`으로 상태 확인부터 정리까지 시연합니다.
4. **데이터 유지** — `-v`로 소개 페이지 폴더를 바인드 마운트하고 호스트에서 고친 내용이 웹 응답에 반영되는지 봅니다. 별도로 이름 있는 볼륨을 연결해 Docker가 관리하는 저장소에 파일을 기록합니다.

**12/10(목) 과제** — 컨테이너 쓰기 영역, 바인드 마운트, 이름 있는 볼륨에 파일을 하나씩 기록합니다. 결과를 먼저 예측한 뒤 컨테이너를 삭제하고 같은 마운트를 연결해 새 컨테이너를 띄웁니다.

**완료 기준** — 컨테이너 쓰기 영역에 기록한 파일은 사라지고 두 마운트의 파일은 남는지 직접 확인합니다. 세 파일의 교체 전후 결과를 표로 남기고, 페이지 편집과 서비스 데이터 보관에 각각 어떤 저장 방식을 선택할지 설명합니다. [Docker 저장소 개요](https://docs.docker.com/engine/storage/)

## 4주차 · Compose로 다른 팀원의 환경에서 재현하기

**교재 범위** — 07-2(환경 변수)와 08-1(웹 동작 방식)을 다시 읽습니다. Dockerfile·이미지 빌드·다중 컨테이너 구성은 [Docker 입문 워크숍](https://docs.docker.com/learn/paths/get-started-with-docker-containers/)과 [Compose 시작 순서 문서](https://docs.docker.com/compose/how-tos/startup-order/)로 보완합니다.

**12/15(화) · 네 파트 시연**

1. **Dockerfile** — `FROM`, `WORKDIR`, `COPY`, `RUN`, `CMD`로 이미지를 작성하고 `docker build -t study-web .`로 빌드합니다. `CMD`와 `ENTRYPOINT`의 역할을 비교하고, 바로 종료된 컨테이너를 `docker ps -a`와 `docker logs`로 조사합니다.
2. **빌드와 배포** — 자주 바뀌는 파일의 복사 단계를 아래로 옮겨 캐시 재사용 범위를 확인합니다. `.dockerignore`로 불필요한 파일을 제외하고 진행자가 `docker login`, `docker tag`, `docker push`로 Docker Hub 게시를 시연합니다.
3. **네트워크** — 기본 bridge와 `docker network create`로 만든 사용자 정의 네트워크를 비교합니다. 같은 사용자 정의 네트워크에서 컨테이너 이름으로 통신한 뒤, Compose에서 서비스 이름으로 DB에 연결합니다.
4. **Compose** — `docker-compose.yml`의 `services`, `image`, `build`, `ports`, `volumes`, `environment`를 읽습니다. 실제 비밀번호는 로컬 `.env`에 두고 저장소에는 `.env.example`만 공유합니다. DB에 `healthcheck`를 정의하고 웹 서비스의 `depends_on`에 `condition: service_healthy`를 설정합니다.

**12/17(목) 최종 과제** — 화요일까지 진행자가 웹 앱 골격을 공유하고 팀원은 Dockerfile, Compose 설정, README를 완성합니다. 공용 랩으로 리허설한 뒤 두 사람이 짝을 이뤄 각자의 앱 저장소 URL과 검증할 커밋을 교환합니다.

**완료 기준**

- 검증자는 짝의 저장소를 지정한 커밋으로 준비해 그 README만으로 설정하고 서비스를 기동합니다.
- DB healthy와 웹 HTTP 200을 확인하고 소개 페이지 응답에서 이번 요청의 방문 번호를 기록합니다.
- 같은 Compose 프로젝트에서 볼륨을 유지한 채 DB 컨테이너를 교체합니다. 교체 전후 DB 컨테이너 ID가 다르고, 조회 전용 `/visits`에서 저장한 번호를 다시 읽으면 통과입니다.
- 대상 저장소 URL과 커밋, 독립 실행 여부, 관찰값을 [결과 양식](https://github.com/wjsworud1025/linux-study-week4-lab/issues/new?template=cross-check.yml)에 제출하고 이슈 링크를 개인 실습 글에 남깁니다. [4주차 검증 절차]({{ '/guides/week-4/' | relative_url }}).
